# Архитектура

`cmd/client`, `cmd/server` — точки входа. `internal/cli` — команды; `internal/client` — HTTPS, кэш и синхронизация; `internal/vault` — криптография; `internal/model` — wire contract и секреты. `internal/api` проверяет запросы и сессии; `internal/store` использует pgxpool. `internal/serverapp` управляет TLS и graceful shutdown. `internal/testutil` содержит тестовые fixtures и не импортируется приложениями.

## Хранение

User: синтетический `BIGINT GENERATED ALWAYS AS IDENTITY` PK, уникальный `login VARCHAR(64)`, bcrypt-хэш, соль и encrypted key check. Session: `token_hash VARCHAR(64)`, `user_id`, срок (24 часа). Record: ключ `(user_id,id)`, `id VARCHAR(32)`, revision, deleted, data и отдельный массив публичных labels. В data зашифрованы тип, title, metadata и всё содержимое. Сессии, записи и журнал операций ссылаются на users.id; API идентифицирует владельца по аутентифицированному логину.

`internal/store/schema.sql` задаёт текущую схему v2. При запуске сервер под advisory lock читает `schema_migrations`: новую базу создаёт сразу в v2, старую схему с ключом login обновляет через `migrations/002_user_identity.sql`. Перенос пользователей, внешних ключей, сессий, записей и журнала операций проходит одной транзакцией. При ошибке ограничения длины миграция откатывается без усечения значений; повторный запуск безопасен. Перед обновлением существующей установки сохраните backup, остановите старый сервер и затем запускайте новую версию: старый бинарник с v2 несовместим.

## Протокол синхронизации

1. Клиент шифрует изменение новым nonce и сохраняет его с исходной ревизией и случайным operation ID.
2. Сначала отправляются удаления, освобождающие квоту данных, затем остальные изменения; внутри каждой группы — в порядке ID записей.
3. Сервер блокирует строку пользователя, проверяет журнал операций, ревизию и квоты; запись и подтверждение фиксируются атомарно.
4. Повтор того же запроса возвращает исходную ревизию. Другой запрос с тем же operation ID получает 409.
5. Клиент удаляет операцию из очереди только после проверки ID, ревизии, признака удаления и шифротекста подтверждения. Некорректный ответ оставляет операцию для безопасного повтора.
6. Клиент получает полный снимок своего namespace с tombstones и заменяет кэш после проверки структуры записей, уникальности ID и квот. Эти же проверки выполняются перед разрешением конфликта. `null` и дополнительные JSON-значения в ответе отклоняются.

Потеря ответа или завершение процесса до сохранения кэша не создаёт дубликат: сохранённая очередь содержит прежний operation ID. Ошибка останавливает текущий push, не откатывая уже отправленные записи.

Tombstone неизменяем. Сохранение локальной версии поверх удаления создаёт новый ID и новое шифрование с соответствующим AAD. После разрешения конфликта возможна новая гонка; она снова обнаруживается по версии.

Квота снимка — 64 МиБ ciphertext; base64 увеличивает HTTP-ответ. Файлы до 8 МиБ обрабатываются целиком. Журнал операций содержит компактные подтверждения без второй копии ciphertext. История и tombstones не очищаются автоматически: очистка потребует протокола согласования со всеми клиентами. Администратор отвечает за место и backups.

CLI создаёт изменения на основе последней известной локальной ревизии, без предварительного обновления перед `edit` или `delete`. Поэтому изменение с другого клиента между чтением и записью обнаруживается сервером как конфликт.

При загрузке кэша проверяются параметры хранилища, ID и ревизии записей, структура мутаций, уникальность operation ID и соответствие шифротекста и признака удаления между очередью и локальными записями. Ошибка проверки останавливает команду до синхронизации и перезаписи файла. Очередь после явного разрешения конфликта может иметь более новую базовую ревизию, чем локальная запись; такой кэш остаётся допустимым.

Очистка истёкших сессий выполняется при запуске отдельной фоновой задачей и затем раз в пять минут; на запрос очистки выделено 10 секунд. Ошибка логируется и не участвует в создании новых сессий. При завершении сервера задача отменяется до закрытия пула.

`GET /v1/records?label=work` возвращает только активные записи владельца с точной публичной меткой. PostgreSQL использует отдельный массив `labels VARCHAR(64)[]` и GIN-индекс. Отфильтрованный ответ не является снимком для синхронизации; удаления и весь набор данных доступны без параметра `label`.

Изменение логина через API не поддерживается: криптографическая привязка AAD по-прежнему включает исходный логин, хотя внешние ключи БД теперь используют стабильный user_id.
